# hdic-update-log

データ修正の経緯を `samples/logs/YYYYMMDD_<対象>_<概要>.md` の形式で記録する手順。
既存の唯一の先例 `samples/logs/20260514_tsj_entries_cleanup.md` の構成を踏襲する。

## いつ使うか

すべての修正コミットに対して機械的に作るものではない。以下のような、
**将来また同じ疑問が生じたときに参照する価値がある修正**で使う。

- 複数ファイルにまたがる修正、または複数件をまとめて直した修正
- 「なぜこの値が正しいのか」の根拠（出典、他資料との突合、ユーザーへの確認内容）が
  コミットメッセージだけでは追いにくいもの
- 同種の問題が今後また見つかる可能性が高いもの（表記ゆれの一括是正、
  ツールで検出した参照切れの解消など）

単純な1行修正で、理由がコミットメッセージ1行で言い尽くせるものは、
無理にログを作らなくてよい。

## ファイル名

`samples/logs/YYYYMMDD_<対象ファイルや辞書名>_<概要>.md`

例:
- `20260514_tsj_entries_cleanup.md`
- `20260819_ktb_tsj_syid_correction.md`

日付はログを書く日（実行日）。

## 構成

先例に合わせ、以下の見出しをこの順で使う。日本語で書く（既存ログの慣習）。

```markdown
# <対象>の<概要>

## 概要

何を、なぜ確認・修正したかを2〜3文で。関連するツール（count_basic_stats.py,
validate_hdic_integrity.py 等）があれば触れる。

## 検出方法

どうやってこの問題に気づいたか。使ったスクリプト・コマンド、実行結果の要点。

## 問題

見つかった問題を箇条書きで。件数、対象ID、具体的な内容。

## 修正内容

ファイルごと・IDごとに、修正前→修正後を示す。判断の根拠（出典、他の行との
突合、ユーザーへの確認で得た情報）も書く。「なぜそう直したか」が本体。

## 結果

修正後の確認結果（count_basic_stats.py / validate_hdic_integrity.py の出力の要点）。
```

## 手順

1. 対象の修正が完了し、コミット済み（またはコミット直前）であることを確認する。
2. 上記の構成でMarkdownを作成する。関連するコミットハッシュがあれば書いてもよいが、
   ログの主眼は「経緯と根拠」であって「diffの再掲」ではない。
3. `samples/logs/` に保存する。
4. データ修正のコミットとは別コミットにする（ログはドキュメントであり、
   データ修正そのものではないため）か、ユーザーに希望を確認する。

## 注意

- ログはユーザー（データの作成者）に確認した内容を正確に反映すること。
  自分の推測や未確認の解釈をログに「確定した事実」として書かない。
  確認が取れていない部分は「未解決」「要確認」と明記する。
