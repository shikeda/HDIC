# hdic-xlsx-reflect

`xlsx/` 配下のExcelファイルで確定した改訂内容を、対応するTSVに反映する依頼を
受けたときの手順。実例: `xlsx/tsj_wakun20260625.xlsx`（「和訓改訂版」シート）を
`TSJ_wakun.tsv` に `sj_w_id` で突合した反映作業（コミット `7f98580`）。

## 前提となる考え方

xlsxとTSVのどちらが「正」かは列によって異なる。実例では、`pos`・`remarks`列は
xlsx側の改訂を反映すべきだったが、`entry_text`等のIDS表記関連列はxlsx側が
古いままだったため反映してはいけなかった（反映するとTSV側の既存の修正を
巻き戻してしまう）。**「どの列を反映するか」は資料批判を要する編集判断であり、
このSkill・スクリプトが自動で決めてはいけない。** 必ずユーザーに列ごとの差分を
提示し、承認を得た列だけを反映する。

## 手順

1. **突合キーの確認**
   対象のTSVとxlsxシートに共通する安定キー列（例: `sj_w_id`）を確認する。
   TSVのヘッダー行と、xlsxシートの1行目（列名）を実際に読んで確認すること
   （推測しない）。

2. **差分レポートを生成する（読み取り専用）**
   ```bash
   python3 samples/scripts/xlsx_tsv_diff.py <xlsx> <シート名> <tsv> <キー列>
   ```
   - 出力される「共通列」ごとの差分件数と例を確認する。
   - `keys only in xlsx` / `keys only in TSV` も確認する。前者は新規行の
     追加が必要な可能性、後者はxlsx側で削除・統合された可能性を示す
     （このSkillは既存行の列更新のみを扱う。行の追加・削除が必要な場合は
     ユーザーに相談する）。

3. **列ごとにユーザーへ確認する**
   差分のあった列を一つずつ、または列のグループとして提示し、
   「この列はxlsxの内容で更新してよいか」を確認する。件数が多い列は
   代表例（スクリプトが自動で出す先頭数件）を見せれば十分。
   **確認を得ていない列は絶対に反映しない。**

4. **承認された列のみ適用する**
   ```bash
   python3 samples/scripts/xlsx_tsv_diff.py <xlsx> <シート名> <tsv> <キー列> \
       --apply-columns col1,col2
   ```
   - 承認された列名をカンマ区切りで指定する。
   - このモードはヘッダー・コメント行・非対象列・非対象行を一切変更しない
     （差分のあった行の、承認された列のセルだけを書き換える）。

5. **`hdic-tsv-validate` skillの手順を実行する**
   `count_basic_stats.py` で構造を確認する。対象TSVが `SJID`/`SYID`等の
   クロスリファレンス列を含む場合は `validate_hdic_integrity.py` も実行する。

6. **`finalize_hdic_edit.py` を実行する**
   ヘッダーのVersion/Last updateを更新する。

7. **diffを提示し、コミットメッセージ案を出す**
   `git diff --stat` の要約と、変更列・変更件数を明記する
   （例: 「和訓改訂版シートとsj_w_idで突合し、pos列(12件)・remarks列(8件)を更新。
   entry_text等はxlsx側が旧版のため据え置き」のように、**反映した列だけでなく
   意図的に据え置いた列とその理由も書く**）。ユーザーの承認を得るまで
   `git commit` は実行しない。

## 注意

- `xlsx_tsv_diff.py` は `openpyxl` を使う（このリポジトリの依存に既に含まれている）。
- 1つのxlsxに複数シートがある場合、`列定義`や`プロジェクト情報`のような
  メタ情報シートを反映対象と誤認しないよう、シート名を必ず確認する。
- xlsx側にしかない列（例: 作業用の `wakun_id_old`、分類用の一時列）は
  比較対象に含まれない（`xlsx_tsv_diff.py` の出力で「columns only in xlsx」
  として報告される）。これらをTSVに新規追加すべきかもユーザーに確認すること。
